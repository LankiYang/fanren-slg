# 凡人修仙 SLG(工作代号,待正式命名)

题材背景:《凡人修仙传》(忘语)世界观。玩法骨架:无尽冬日(Whiteout Survival)+ 万国觉醒(Rise of Kingdoms)两款 SLG 的系统重组,面向 web 端。

## 已锁定的产品决策(2026-09-17)

> **范围更新(2026-09-18)**：用户明确要求“能真正在地图上对战”，因此共享大地图和地图行军从二期提前为当前联机主流程。下面关于“二期暂缓”的旧记录仅保留为立项历史，不再作为当前实现边界。

1. **角色/世界观处理**:原著角色(韩立、南宫婉、黄枫谷、七玄门等)先作为**内部原型占位符**,用于快速验证玩法是否好玩。**对外正式发布前必须替换成原创角色/门派**,当前阶段不考虑 IP 授权谈判——这意味着任何在此基础上产出的美术资产、文案都要按"临时占位、终将替换"的前提来做,不要在占位阶段投入定稿级别的美术/文案成本。
2. **当前开发范围**:单城建造 + 秘境推图(PvE)+ 宗门协作 + 共享大地图战争。地图战争采用服务端权威的异步实时行军 MVP，玩家坐标、道路、行军、据点到达结算和跨玩家可见性都已进入主流程。

这两条决策若要推翻,需要用户明确重新拍板,不要在后续设计讨论中自行放松。

## 当前进度(2026-09-18)

一期 MVP **已可运行**：`npm install && npm run dev`（网页端口 5180，多人 API 端口 5181）。

技术栈：Vite + React 18 + TypeScript + zustand；洞府养成暂存 localStorage，战区已接入 TypeScript Node 多人服务端。

> 当前包含「赛季战区」多人地图战争：游客身份、共享坐标地图、道路、玩家位置、可见行军、抵达后战斗结算、跨宗门攻防、服务端权威兵损/冷却、宗门榜、个人榜、战报、幂等出征和真实好友系统已经可玩。洞府境界、修士、功法、法宝、丹药、寻道灵装会生成统一 `BattleProfile`，服务端重新计算行军与守军战力；占领据点的持续收益会反哺洞府资源，战报奖励按 ID 去重入账。好友系统支持玩家搜索、申请/同意/拒绝/删除、在线状态、地图位置和行军目标同步。多人服务端现在支持 PostgreSQL 事务存储和 JSON 开发 fallback；生产模式通过连接池、行级锁和事务提交保证多实例并发一致性。它是异步实时地图战争 MVP，不是 WebSocket 帧同步；完整边界见 `docs/specs/multiplayer-foundation.md` 和 `docs/specs/warfront-map-mvp.md`。

战区新增战争令和宗门驻防：出征消耗战争令并随时间恢复；占领后可把个人兵力派入据点，援军会成为真实守军，其他宗门玩家可侦察并争夺。

只启动 `vite` 不会启动多人 API；开发时使用 `npm run dev`。没有设置数据库连接时，服务端状态保存到 `server/data/state.json`；设置 `FANREN_STORAGE=postgres` 和 `FANREN_DATABASE_URL` 后使用 PostgreSQL。

### 真实服务端启动

本地有 PostgreSQL 时，复制 `.env.example` 为 `.env`，填写连接串后运行：

```bash
npm run server
```

没有本地 PostgreSQL 时，可直接启动数据库容器和 API：

```bash
docker compose up -d postgres api
npm run dev:web
```

数据库首次启动会执行 `server/db/migrations/001_world_state.sql`，创建迁移表和权威世界状态表。API 健康检查会返回 `storage: "postgres"`，确认请求已经进入数据库模式。

### 三道质量闸门

```bash
npm run check     # = tsc + audit + sim，改完数值跑这一条即可
npm run sim       # 30 天节奏模拟，验里程碑是否达标
npm run audit     # 18 类数值审计，查死锁/单调性/跨模块一致性/量纲
npm run expedition # 30 天远征循环、路线类型与长期兑换出口模拟
npm run warfront  # 战区出征、兵损、占领、收益、冷却的领域自测
npm run stage     # 秘境失败兵损、不推进、补兵重试自测
```

三者都必须绿。`sim` 验「跑起来是不是那个节奏」，`audit` 验「数本身有没有算错」——
这是两件事，模拟器全绿时 audit 仍抓出过 2 个真问题。

注意 `tsconfig.json` 的 `include` 含 `sim`：这两个脚本和游戏共用 `balance.ts`，
漏检会让模拟器带着未定义引用跑到运行时才炸（已经发生过一次）。

### 已实现并实测通过

- **洞府主城**：10 座建筑四排布局；洞府等级封顶其余建筑（熔炉机制）；洞府升级另需 2 座产出建筑达标（主建筑 gate，同时精准控节奏）；**洞府外观随等级分三档**
- **洞府视觉动效**：产出建筑有分类型灵气、萤火、矿火和交易灵流；功能建筑有符印、炉火、斩击和护宗环。具体分层和后续高保真路线见 `docs/specs/visual-motion.md`
- **四资源循环**：实时产出 + 仓库上限（满仓停产，催上线的核心杠杆）+ 离线结算（8h 封顶、70% 折算、回流弹窗告知损失了多少）
- **建造队列**：1 条免费 + 1 条可开辟；单次建造 48h 封顶
- **境界突破**：13 档（炼气 6 / 筑基 3 / 结丹 4），提供产出与战力乘区
- **演武场练兵**：三兵种三角克制 + 兵力上限
- **出战编队**：**统兵上限**（一次只能带 55% 兵力）+ 按敌方兵种分配各兵种出战数。
  实测同样占满名额，均分 11.1 万 vs 择优 16.7 万，差 50% —— 克制关系是真决策而非被动结算
- **秘境推图**：8 章 40 关，**每章专属妖兽立绘**，难度与奖励由曲线生成；胜败都会产生有限兵损，失败不推进且不发首通奖励，补兵后可重试
- **天机远征**：每日轮换主题的五层路线图，每层二选一；破阵/首领有四幕战斗演出，采灵/护送/天机提供非战斗路线；远征令恢复、风险收益选择、失败兵损与路线保留、周里程碑、28 天游历和远征商店组成 30 天循环。完整规则见 `docs/specs/expedition-longterm.md`
- **寻道主线循环**：主城内可连续点击“寻道·参悟”，每次稳定掉修为和四类灵材，机缘充足时提高良品/上品/天成灵装概率；灵装三槽自动换装，重复物转炼器尘并可淬炼，修为条与洞府、突破资源共同推动境界。机缘耗尽后仍可免费静心参悟，不把主线锁死。男修/女修只影响身份叙事与立绘，不做数值职业差异。规则和迁移边界见 `docs/specs/seek-main-loop.md`
- **修士养成**：4 名，按专精加成对应兵种，通关解锁
- **功法（藏经阁）**：采集/攻伐/营造三支共 8 条永久增益，主吃灵气
- **丹药（炼丹房）**：3 种限时增益，炼制→服用，主吃灵药，制造「上线嗑一颗」的日常循环
- **法宝（炼器阁）**：3 件装备按兵种加成，主吃矿灵材
- **合围妖兽**：宗门协作 PvE，4h 冷却，按伤害占比分 4 档发奖（单机版同门伤害由 NPC 按比例模拟）
- **成长任务**：12 条，悬浮追踪器常驻显示下一步，兼作长线引导与留存钩子
- **新手引导**：8 步阻断式蒙层引导，引导 NPC「南宫婉」双姿态立绘
  （**原著角色占位**，与修士名册中同名角色为同一人；按决策1，发布前须连同立绘替换为原创）。
  四块遮罩围出孔洞（不是盖一整块再抠洞——那样洞里的元素依然点不到），
  孔洞逐帧跟随目标，点击型步骤只有高亮处可点。目标落在底部时对话框自动翻顶，
  避免立绘压住高亮目标。可随时跳过，状态持久化不重复出现。

四种资源各有专属去向（灵石=通用 / 灵气=功法 / 灵药=丹药 / 矿灵材=法宝），
而不是全部涌向建造 —— 由 audit 第 18 项强制校验。

### 美术素材生产流水线

素材全部由 `gen-image.cjs` 生成（Cloudsway 网关 / `MaaS_Ge_3.1_flash_image_20260528`），流程为「写 prompt → 生图 → 视觉检验 → 抠底 → 裁边 → 压缩」：

```bash
node gen-image.cjs --batch art/batch2-buildings.json   # 批量生成
node remove-bg.cjs                                     # 抠白底（flood-fill，保护主体内部浅色）
node trim.cjs                                          # 裁掉透明边距，否则 UI 里按百分比渲染会显得很小
node optimize-sprites.cjs                              # 降采样 + 转 WebP，产出打包用素材
```

**目录分工**：前三步都在 `art/masters/`（PNG 母版工作区，29MB，已进 `.gitignore`）里原地进行；最后一步把母版降采样转成 `src/assets/sprites/**/*.webp`（0.76MB，入库并参与打包）。`src/ui/util.ts` 的 `sprite()` 用 `import.meta.glob` 匹配的是 `.webp`，**只有跑完第四步改动才会出现在页面上**。

风格统一靠 prompt 里固定的风格后缀：等距 3/4 俯视、纯白底、左上打光、青绿+暖金配色。`art/*.json` 是各批次的 prompt 存档，改素材时照着改再重跑即可。

降采样档位按实际渲染尺寸 ×3（覆盖 3x DPR）定：建筑最大边 512（场景里最大占 32% 屏宽 ≈154px）、修士/兵种/妖兽 256（都是 54×54 缩略图）、图标 128（顶栏 20×20）。背景图是唯一**按高度**限制的——横图用 `object-fit: cover` 填竖屏时绑定轴是高度而非宽度，按宽度限制反而会把它压到需要放大 1.23× 才能铺满，所以保住母版原生的 768 高。

**母版不在仓库里**：`art/masters/` 被 gitignore，克隆下来的仓库只有 WebP 成品。要重新生成或调整素材，需要先拿到母版（或用 `gen-image.cjs` 重跑）。

## 数值设计说明（立项会材料）

全部曲线集中在 `src/game/balance.ts`，游戏与模拟器共用同一套函数，
不存在「模拟器验过的数」和「线上跑的数」分叉的可能。

**标定口径**：成本曲线按「升一级 ≈ 攒多少小时产出」标定，记 H(L)。
设计意图 H(1)≈0.9h（前期几十分钟一级）→ H(24)≈40h（后期按天等，付费位）。
跨度约 44 倍，因此 costR/prodR ≈ 44^(1/23) ≈ 1.18。
**成本增速必须明显高于产出增速**，否则后期资源过剩、采集循环失去意义
（首版 costR 只比 prodR 高一点，模拟出来资源不足仅 113 次 vs 队列占满 1227 次，等于资源不构成约束）。

**结构性约束**（违反必然卡死，已固化为 `npm run audit` 的断言）：
1. 四座产出建筑解锁等级必须为 0，**且开局等级必须为 1**。只放开解锁不够——
   主建筑升级会吃光开局资源，导致没钱建产出建筑，对应资源零产出、永久卡死。
2. 仓库上限不配独立曲线，而是定义为「下一级洞府开销 × 2.6」。
   曾经两条曲线各配各的，只调了成本没调仓库，洞府 21 级时成本超过仓库上限，满仓也买不起。
3. 开局资源每项都必须 ≤ 1 级仓库上限，否则白送的资源一进游戏就被截断。

这三条都是实际踩过的坑，不是假想风险。详见 `sim/audit.ts` 与 `sim/simulate.ts` 的注释。
