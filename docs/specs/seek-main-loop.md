# 寻道主线与随机掉落规格

状态：已落地第一版
日期：2026-09-20

## 1. 调研结论

本轮通过公开攻略资料核对《寻道大千》的玩法结构，重点参考了 [《寻道大千》详细攻略各类玩法解析攻略（新手福音）](https://www.bilibili.com/opus/1005542429180297219)，并用搜索结果交叉确认了仙树、砍树体力、灵兽、神通、装备、斗法和妖盟等关键词。

可借鉴的是循环结构，不是名称、文案、美术和数值：

| 观察到的结构 | 本项目的转译 |
|---|---|
| 高频砍树，短时间内获得装备和资源 | 主城内的「寻道·参悟」按钮，点击立即掉落修为、四类灵材或灵装 |
| 仙树升级提高后续装备收益 | 洞府与境界提高寻道的修为、灵材和装备评分基线 |
| 装备、灵兽、精怪、神通形成多层养成 | 灵装三槽接入现有法宝/功法/兵种体系；重复灵装转炼器尘，可淬炼当前灵装 |
| 斗法、妖盟、妖王、活动提供长期目标 | 寻道里程碑接入秘境、宗门、战区和远征，不单独制造孤岛玩法 |
| 随机传说三选一、概率反馈和每日内容 | 本版先做单击单次掉落、透明保底和机缘恢复；三选一作为后续活动卡池，不把主线锁在抽奖上 |

不直接照搬的部分：原游戏的角色、灵兽、精怪、神通名称和美术；广告观看、付费抽取、内部号等商业机制不进入本项目的主线规则。

## 2. 核心循环

```text
点击寻道
  -> 修为稳定增加（每次都有）
  -> 灵石/灵气/灵药/矿灵材随机到账（受仓库上限保护）
  -> 机缘充足时提高良品、上品、天成灵装概率
  -> 灵装自动比较换装；重复灵装转炼器尘
  -> 炼器尘淬炼三部位灵装，进入战力乘区
  -> 修为条满 + 洞府/资源达标 -> 境界突破仪式
  -> 境界提高寻道基线，继续推秘境、远征、宗门和战区
```

### 点击与机缘

- 每次点击都结算修为和基础灵材；机缘为 24 点，上限 24，每 90 秒恢复 1 点。
- 机缘耗尽后按钮变为“静心”，依然有修为和低概率灵装，不会出现点击无收益的硬阻断。
- 连续点击、暴击机缘和自动换装提供即时反馈；每日次数、总次数和寻道里程提供短中长期目标。
- 仓库上限仍由洞府曲线控制，掉落不能绕过原有资源结构。

### 掉落与保底

- 机缘充足时：凡品为基础，良品约 25% 档，上品约 9% 档，天成约 1.2% 档；静心状态降低高品质概率。
- 连续 10 次没有上品或天成时，第 10 次按上品处理；连续 40 次没有天成时，第 40 次按天成处理。
- 保底状态写入 `SeekDrop.pityTriggered` 并在掉落演出中显示“保底天机”，概率不是黑箱。
- 灵装槽位为灵兵、法衣、灵佩。高评分灵装自动换上，低评分重复灵装按评分转换为炼器尘。
- 本地点击随机源封装在 `resolveSeekDrop`，模拟器可注入固定随机源；后续接入真实服务器时由服务端复用同一领域规则并返回结果。

## 3. 与既有系统的耦合边界

- `src/game/seek.ts` 只负责掉落规则、机缘、保底、修为门槛和灵装评分，不依赖 UI。
- `GameState.character` 保存男修/女修选择；两者只影响称谓、开场旁白和立绘，不改变战力、掉率或资源产出。
- `GameState.seek` 保存寻道状态，旧存档由 `loadState` 补默认字段，不清空原有洞府、战区、远征和好友数据。
- `breakthrough` 现在同时检查洞府、原有突破资源和当前境界修为；成功后扣除当前境界修为，保留溢出之外的清晰阶段感。
- `compute.troopPower` 把当前三部位灵装评分映射为最多 35% 的全局小乘区；兵种克制、编队和地图战斗规则不被替换。
- 掉落资源通过原有 `currentCap` 和 `makeFloats` 入账，因此顶栏飘字、仓库封顶、离线结算和任务系统仍使用同一套资源边界。

## 4. 30 天支撑

寻道领域的 `sim/seek.ts` 用固定随机序列模拟每天 24 次操作、连续 30 天，检查：

- 720 次点击都有修为与掉落结算；
- 三个灵装槽能被填满并进入战力计算；
- 上品与天成掉落可见，普通保底不超过 10 次空窗，天成保底不超过 40 次空窗；
- 修为能推进至少 4 次境界进阶；
- 寻道里程碑在 10/50/150/300/600 次提供长期领取目标。

它与现有 `sim/simulate.ts`、`sim/expedition.ts` 互补：洞府模拟验证资源/建造节奏，远征模拟验证路线内容，寻道模拟验证高频点击和随机反馈。

## 5. 迁移与后续

当前版本的洞府养成仍存 localStorage，战区已经有服务端权威 API。若把寻道接入多人正式服：

1. 客户端只提交 `seek` 意图和幂等请求号，不提交随机结果、修为数值或装备评分。
2. 服务端事务读取玩家 `seek` 状态，校验机缘、保底和仓库容量，生成 `SeekDrop` 后原子更新玩家状态。
3. 返回 `SeekDrop` 与新版本号；客户端用版本号防止重复点击、刷新重放和多标签页覆盖。
4. 灵装表、掉落权重和保底阈值放入版本化配置，保证未来移动端、桌面端与 Web 端一致。
